**Sixth pass — RADV thread traces, 2026-09-22.** RGP thread traces now import through the same `rocprof-trace-decoder` as raw ATT. The deciding experiment settled the cause. rocprofv3 ATT on this gfx1151, with the same kernel and decoder, is clean at wave32 and wave64. So the fault was RADV's thread-trace **token mask**, which enables ALU/VMEM execution tokens that the decoder has no encoding for, not the decoder's GFX11.5 support. The earlier "clock problem" diagnosis was wrong; the timestamps were desync symptoms.

- Execution tokens are blanked to NOPs before decoding (length and timing preserved), and code objects are placed at their RGP loader-event addresses, matched by pipeline hash.
- Each trace must pass four checks: no unsizeable headers, no reported data loss, a steady clock against a steady realtime cadence, and every timestamp inside its shader engine's window. The fourth caught a real wave32 capture whose SE1 waves spanned 86 M cycles while passing every per-wave invariant; tightening the realtime check to require a steady cadence then caught it earlier. (The cadence requirement was too strict for real workloads and was replaced in the seventh pass.)
- **Occupancy mode is exact at any scale**: 4,096 waves for a 4,096-workgroup dispatch.
- **Per-instruction attribution from instruction-timing captures is not reliable and is not claimed.** RADV reports most VALU execution through the blanked tokens. Busy instruction-timing captures are rejected outright; counters still import.
- The counter axis was also wrong: SPM timestamps are the 100.003 MHz GPU timestamp, not shader clocks, and the committed `spmWindow` was 3× too long. Fixed.
- `decoder.rs` now surfaces the decoder's own INFO warnings for **ROCm** raw ATT too; they had been silently dropped.

Two vendored fixtures cover both capture modes, and 14 tests cover them, 2 of which need the decoder. The desktop open dialog had never listed `.rgp`, so no user could have selected a RADV capture from the GUI; it does now. A browser test built from a real importer bundle checks that the counters, trace workspace and attribution warning all render. Full attribution needs one upstream change, recorded in blocked-inputs §3.

**Seventh pass — full RADV compute profiling, 2026-09-22.** Measured on gfx1151 with Mesa 26.2.0; details and numbers are in [blocked-inputs.md](blocked-inputs.md) §3.

- **Per-instruction attribution.** `docs/radv-rocprof-compat.patch` adds an opt-in `RADV_THREAD_TRACE_ROCPROF_COMPAT` that programs aqlprofile's GFX11 token-exclusion set. It was built from a copy of Mesa 26.2.0, and with it the unmodified decoder attributes every instruction exactly, up to 4,096 × 4,096. RADV's default mask attributes 8 of 1,052 on the same kernel, so the sixth pass's "undercounted" understated the loss. The importer now infers three modes from the stream: full, default mask with execution tokens removed, and occupancy.
- **Real workload.** Two llama.cpp prompt-processing runs, 4,154 submits, all import. This found a defect: the sixth pass's realtime-cadence check rejected 93% of them, because realtime tokens pause while the GPU idles. The check now tests whether the shader clock nearly stopped across a gap. RADV inhibits clock gating while tracing, so that cannot happen legitimately, and the wave32 capture the old check was added for is still rejected.
- **Kernel names and dispatch grids.** RADV's RGP markers are read from userdata register tokens in the trace. Kernels are named after the application's debug labels, all ggml shaders with `GGML_VK_DEBUG_MARKERS=1`; RADV's internal copy shader after `vkCmdCopyBuffer`; and otherwise by API PSO hash, where the old fallback was a raw address. Markers are paired with the decoder's dispatch records, gated on count, queue and pipeline agreement, and every `vkCmdDispatch` gets its grid. The decoder's workgroup field was the raw register, with RADV's partial count in the high bits; it is now masked to `NUM_THREAD_FULL`, which affects ROCm raw ATT too. On the vendored llama submit, occupancy per kernel equals marker grid × waves per workgroup for all eight kernels.
- **Raw counters.** Mesa 26.2's `RADV_SPM_COUNTERS_CONFIG` imports as hardware counters, and RADV's own counter descriptions now reach the counter view. Measured against known totals, the raw values are incomplete on this GPU (partial TA instance coverage, SQ reads zero), and the importer warns accordingly.

Four new fixtures and six new tests cover this, three of which need the decoder; there is one new browser test. The compat option exists only as this project's patch. Whether to propose it to Mesa is the user's decision, and nothing has been submitted anywhere.

**Eighth pass — single-shader tuning for Vulkan, 2026-09-23.** The Vulkan counterpart of the HIP kernel-tuning session, described in README's "Shader tuning" section. A capture layer (`tools/vkcap/vkcap_layer.cpp`) records one dispatch, including its bound buffers before and after it. A replay harness (`vkreplay.cpp`) times the dispatch in isolation and validates it against the application's own output. `shader_worker.py` recovers the GLSL recipe of a ggml shader by SPIR-V identity: it ignores the fp16 float-control instructions ggml adds at run time and reapplies them to every variant. Qualified end to end through MCP on llama.cpp's IQ4_NL matrix multiply on gfx1151:
- capture 2.7 s, source search 1.6 s, recipe recovery 4.4 s, runs about 1.4 s;
- the captured shader replays bit-exactly, and a comment-only edit compiles back to identical SPIR-V;
- shared-memory row padding 4 → 2 measured 36% (at `-ub 512`) and 28% (at `-ub 256`) faster in isolation, with bit-identical outputs.

That is a measurement of the isolated dispatch, not an application speedup.

**Whole-application check, same day.** A separate Vulkan-only clone of llama.cpp at `4ceb17191`, with a test-only environment override for the pad's specialization constant, so both pads ran from one binary. The user's llama.cpp tree was not touched.
- **Benchmark.** `llama-bench` on Qwen3.5-9B IQ4_NL, three interleaved rounds of five repetitions: pp512 is about 8% faster (mean 1094 → 1180 t/s on Mesa 26.2.0, 1079 → 1169 on the system Mesa 26.0.8). tg128 is unchanged.
- **Per operation** (`GGML_VK_PERF_LOGGER`, Mesa 26.2.0): m=8192 k=4096, the captured shape, −28.5%; m=4096 k=4096 −30.7%; FFN down (k=12288) −7.4%; FFN gate/up (m=12288), 35% of GPU time, −3.9%. The FFN gate/up dispatch, captured and replayed, shows −30% in isolation. For the shapes that dominate, replay overstated the in-application gain several-fold.
- **Clocks.** Pad 2 starts 11% faster, then falls back as the clock drops from about 2.7 GHz to 2.4 GHz, at lower package power than pad 4. Replay alternates each dispatch with buffer restores; over 2,000 iterations its clock stayed at 2.9 GHz.
- **Driver.** The tuning session had inherited the profile run's patched Mesa 26.2.0. The system Mesa 26.0.8 keeps 192 VGPRs and 8 waves at pad 2 (replay −16%, in-application −11 to −15%); 26.2.0 drops to 120 VGPRs and 12 waves because the shared-memory size falls from 23.5 to 21.5 KB.
- **Correctness.** `test-backend-ops` MUL_MAT (1128/1128) and MUL_MAT_ID (937/937) pass with pad 2 on both drivers.
- **Spec.** Pad 2 makes the cooperative-matrix load stride 72 bytes, which violates `VUID-RuntimeSpirv-OpCooperativeMatrixLoadKHR-08986` (16-byte alignment). Pad 4 is 80 bytes, which is why it was chosen. RADV computes correctly because it does not rely on the alignment, so the change is not upstreamable as is. A compliant route to the same occupancy would keep pad 4 and free about 2 KB of shared memory elsewhere; that is untested.

Tool follow-ups this exposed, none done:
- **In-application A/B.** The capture layer could substitute a variant's SPIR-V into the running application, so a candidate is timed in context without rebuilding it.
- **Cross-driver replay.** `vkreplay` refuses a capture made on another driver with a bare `vkCreateDevice failed (-8)`. It should name the unsupported feature, or drop it with a note.
- **Driver in results.** Replay results and sessions should show the driver version they ran on.

**Ninth pass — why replay and application disagree, 2026-09-23.** All measurements are on the FFN gate/up matmul (m=12288) with Mesa 26.2.0.

Method:
- `vkreplay` gained `--mode sustained`, `--memory device|app|gtt`, `--flush-mb` and `--counters` (VK_KHR_performance_query).
- In-application times per dispatch came from a test-only line in ggml's perf logger, in a scratch copy of llama.cpp.

Four causes, all measured:
- **Placement.** The VRAM carve-out on this APU is 2 GB, mostly used by the desktop, so llama.cpp's weights live in GTT, while a replay's buffers fit in VRAM.
  - In the application, pad 2 takes 1950–3050 µs per layer, and each layer's time is stable across repetitions. Pad 4 takes 2450–2650 µs everywhere.
  - Forcing every weight into GTT (`GGML_VK_PREFER_HOST_MEMORY`) removes the uniformly fast final layers.
  - Two layers 50% apart in the application replay identically in VRAM (1693 and 1697 µs).
  - Fresh GTT allocations in replay give 2120–2953 µs for pad 2 and 2303–2394 µs for pad 4.
- **Cycles, not clock.** At a steady ~2.45 GHz, the GTT slowdowns are up to 45% more GPU cycles.
  - The L2 hit rate is 79% at 8 waves regardless of placement.
  - At 12 waves it is 53% in VRAM and 45–51% in GTT, with lower L1 hits.
  - More workgroups in flight cost cache hits, and scattered 4 KB pages cost more. This fits physically addressed cache and channel mapping, or address translation; the available counters cannot separate the two.
- **Sustained load.** Back to back, cycles do not change, but the clock falls from about 2.45 GHz to 2.37 GHz at 8 waves, and to 1.87–1.92 GHz at 12 waves. Replay's default restore between dispatches never gets there.
- **Sampling.** A session captures one layer's dispatch from one allocation. The application averages 64 dispatches over 64 weight regions.

**Spec-compliant alternative to pad 2.** Keep pad 4 and stage f16 results in `buf_a`. The main loop ends on a barrier, so `buf_a` is free by the time results are stored.
- **Compiler:** shared memory drops from 23.5 to 21.5 KB, giving 120 VGPRs and 12 waves on Mesa 26.2.
- **Correctness:** outputs are bit-identical, and `test-backend-ops` MUL_MAT (1128/1128) and MUL_MAT_ID (937/937) pass on 26.2 and 26.0.8.
- **Replay:** −24% in VRAM and −15% sustained in GTT, with the same per-allocation spread as pad 2.
- **Application:** pp512 +6% (1099 → 1169 t/s). FFN gate/up −1.5%, FFN down +0.2%, the other IQ4_NL shapes −22%.
- **Mesa 26.0.8:** 192 VGPRs and 8 waves, no gain.
- **Scope:** bf16 variants are excluded, because their `buf_a` holds bf16.

The patch is in `.synagent/archive/`; nothing has been sent anywhere.

For these matmuls, higher occupancy trades L2 hits for latency hiding. It pays only while the weights sit in VRAM-like memory and the clock holds. A larger carve-out (a firmware setting) would test the first condition; that is untested.

RADV's instruction counters report VALU equal to SALU and VMEM equal to SMEM, so only cycles and hit ratios were used.

**Tenth pass — replay conditions and counters in sessions, 2026-09-23.** Vulkan tuning runs take `conditions`:
- `mode`: stateless or sustained;
- `memory`: device, app, gtt, or auto (gtt on integrated GPUs);
- `flushMb`;
- `repeats`: replays with fresh allocations, reported as a spread.

`autoCounters` (default on) adds GPU cycles, the clock the dispatch ran at, and L0, L1 and L2 hit rates. The UI and MCP both expose them, with Best case and Application-like presets.

- **Validation.** A sustained run validates two back-to-back dispatches, so a dispatch that reads its own output is caught.
- **Deltas.** They pair a run with the latest run under the same conditions, and each run records its driver version and memory placement.

**Checked end to end through MCP** on the FFN gate/up dispatch, Mesa 26.2, with the pad-4 staging edit (in µs):

| Conditions | Baseline | Edit | Change | L2 hit rate |
|---|---|---|---|---|
| Best case | 2370 | 1812 | −23.6% | 79% → 54% |
| Application-like (sustained, GTT, 3 replays) | 2472 | 2513 | +1.7% | 79% → 47% |

- **Spread:** the replay spread doubled, from 5.7% to 12.2%.
- **Prediction:** inside llama-bench the same edit measured −1.5% on this shape, which the application-like conditions predicted.

Four worker tests, and assertions in the browser test, cover the conditions, the counter metrics, delta pairing and the sustained check.
