## MUST-FIX

### M1. `.rgp` import hard-codes the 256 MiB per-file cap, bypassing `caps.rs` — `ROCPROF_MAX_FILE_MIB` is silently ineffective for RGP, and the docs claim otherwise
- **Where:** `crates/profile-core/src/rgp.rs:4` (`const MAX_FILE: u64 = 256 * 1024 * 1024`), enforced at `:1050-1051` with the literal message `"{} exceeds the 256 MiB per-file import limit"`. Shared getters at `caps.rs:47-53` (`max_file_mib()`/`max_file_bytes()`, default `MAX_FILE_MIB_DEFAULT = 256` at `:23`, override `ROCPROF_MAX_FILE_MIB`). Every sibling importer uses them: `import.rs` (JSON/CSV/wave sidecar), `irpf.rs`, `loom_report.rs`.
- **Failure scenario:** operator sets `ROCPROF_MAX_FILE_MIB=1024` (the documented Upgrade workflow). A 512 MiB `.irpf`/`.csv`/`.json` imports; a 512 MiB `.rgp` is still refused with a message naming the fixed 256 MiB. The env var never reaches the `.rgp` path and the message does not interpolate the effective value.
- **Doc contradiction (the sharp part):** `docs/architecture.md:99` — "The record cap, **per-file size cap**, hidden-latency token cap and ATT-manifest file caps are resolved through `crates/profile-core/src/caps.rs`" — plus `README.md` "Current limits" and `CHANGELOG.md` ("the rejection message interpolates the effective value", "applied across desktop, headless CLI and MCP") are literally false for the reachable `.rgp` picker path (`src/bridge.ts:100-118` accepts `.rgp`; `project.rs` routes it with no outer size check).
- **No test guards it:** `crates/profile-core/tests/configurable_caps.rs` exercises the file-cap override only for CSV; `tests/rgp.rs` has zero file-cap assertions.
- **Fix direction:** route rgp.rs's size check through `caps::max_file_bytes()` and interpolate the effective value, **or** record the `.rgp` carve-out explicitly in README/limits.md/architecture.md. Do not silently widen it — the caps module is a deliberate rejection-boundary design (`caps.rs:21` already scopes itself to "sidecar / JSON / CSV inputs", so the carve-out is plausibly deliberate and merely undocumented).

### M2. Desktop `live_profile_trigger`/`stop` pass a throwaway cancellation flag; the MCP arms pass the real one
- **Where:** `src-tauri/src/mcp.rs:359` (`live_profile_trigger`) and `:370` (`live_profile_stop`) call `profile_trigger_core`/`profile_stop_core` with `&AtomicBool::new(false)` — a fresh temporary with no stored owner. The MCP arms `:1366`/`:1368` pass the real per-request `&flag` (created `:909`, cloned into `Active.cancel`, set by `Control::cancel`). `live_profile_start`/`status` correctly match their arms (those cores take no flag).
- **Failure scenario:** user clicks Stop in the desktop Live-profiling panel with an open triggered/timed window. `profile_stop_core` enters its up-to-180 s detach wait (`:1775`) polling the throwaway flag; because the temporary has no stored owner, `Control::cancel`/`mcp_cancel`/`shutdown()` can never reach it (`self.active` is `None` during a desktop op), and tokio `spawn_blocking` tasks cannot be aborted. The UI blocks the full 180 s, holds the `live_profile` mutex, and cannot be cancelled by closing the panel — while the identical MCP `profile_stop` aborts promptly on client cancellation.
- **Severity disputed by the debate** (MEDIUM "unacknowledged surface divergence" vs HIGH "180 s block, no cancel path"). Facts undisputed; fix is the same either way. Complements KB `ba3416f3` (mutex freeze).
- **Fix direction:** store a cancellation flag on `Control` (as `Active.cancel` already does for MCP) that the desktop commands share. Passing a different temporary cannot fix it — the flag needs a stored owner.
